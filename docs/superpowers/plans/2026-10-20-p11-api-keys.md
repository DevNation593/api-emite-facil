# Plan 11 — API keys para sistemas externos

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** que un ERP, un punto de venta o una tienda en línea facturen contra la API con una API key
de la empresa, enviada en la cabecera `X-Api-Key`, sin el inicio de sesión de una persona.

**Architecture:**

- Un paquete nuevo, `com.example.einvoice.apikey`, contiene todo lo propio de las keys:
  - el formato y el hash;
  - la tabla y el servicio;
  - el controlador de gestión;
  - el filtro que autentica.
- `TenantAccess` gana `apiKeyId`, y `TenantAccessResolver` arma el acceso de una key con rol BILLER a
  nombre de quien la creó. Los `requireWrite` y `requireOwner` que ya existen hacen el resto.
- La auditoría guarda `api_key_id` con una firma nueva de `AuditLog.record`.
- La web añade una sección en Integraciones, y las pruebas con navegador recorren
  crear → facturar con la key → revocar.

**Tech Stack:** el de los planes anteriores; nada nuevo.

**Repositorios:** la API en `api-emite-facil` (clon `D:\Proyectos Personales\backend-emite-facil`) y la
web en `client-factura-facil`. Llevan la misma rama, `p11-api-keys`, salida de
`p10-autenticacion-propia`. En la API la rama ya existe con la especificación (c118133).

**Spec:** [docs/superpowers/specs/2026-10-15-api-keys-design.md](../specs/2026-10-15-api-keys-design.md).

## Global Constraints

- Transporte: solo la cabecera `X-Api-Key`. `Authorization: Bearer` sigue siendo solo para JWT.
- Formato: `efk_<publicId>_<secreto>`. Regex: `^efk_[A-Za-z0-9]{12}_[A-Za-z0-9_-]{43}$`. El secreto
  son 32 bytes de `SecureRandom` en base64url sin relleno.
- Solo se guarda el SHA-256 en hex del secreto, y se compara con `MessageDigest.isEqual`. El valor
  completo solo aparece en la respuesta 201 de creación. Nunca va a logs, auditoría ni métricas.
- Rol efectivo de una key: siempre `BILLER`. Actúa a nombre de `created_by`.
- Hasta 10 keys activas por empresa. Nombre de 1 a 80 caracteres tras recortar, sin caracteres de
  control y único entre las activas sin distinguir mayúsculas. No caducan; revocarlas es inmediato
  e irreversible.
- Códigos de error, exactos:

  | Estado | Código |
  |---|---|
  | 400 | `CREDENTIALS_AMBIGUOUS` |
  | 401 | `UNAUTHENTICATED`, mensaje "Se requiere un token de acceso válido" (el que ya existe) |
  | 403 | `API_KEY_NOT_ALLOWED` |
  | 409 | `API_KEY_LIMIT` |
  | 409 | `API_KEY_NAME_TAKEN` |
  | 404 | `API_KEY_NOT_FOUND` |
  | 403 | `TENANT_FORBIDDEN`, `ROLE_FORBIDDEN` (los que ya existen) |

- Auditoría: `API_KEY_CREATED` y `API_KEY_REVOKED`, con entidad `API_KEY` y metadatos `{name}`.
- Migración `V16__api_keys.sql` (solo avanza). El contrato pasa de `0.14.0` a `0.15.0` en el primer
  commit que cambia la API. La web copia el contrato y regenera `src/api/schema.ts`.
- Comandos:
  - API: `./mvnw -B verify`, con `-Djacoco.skip=true -Dit.test=<Clase>` en las corridas parciales.
  - Web: `npm run lint && npm run typecheck && npm test && npm run build`, y `npm run api:check`.
  - Navegador: `npm run stack:up && npm run e2e` en `e2e/`, con la web de la misma rama clonada al
    lado. Antes, `JAVA_TOOL_OPTIONS` con otro `jdk.net.unixdomain.tmpdir`, como dice `e2e/README.md`.
- No levantar nada en Docker para correr la API contra el ambiente de Stiwar. Testcontainers y la
  pila de `e2e/` son las de siempre.

## Review Focus

1. **Valor de la key con espacios alrededor o con salto de línea final** (copiado desde un correo o
   un `.env`): debe funcionar igual. `ApiKeyCredential.parse` recorta antes de validar (Task 1).
2. **Cabecera `X-Api-Key` presente pero vacía:** debe dar 401, no tratarse como si no viniera y
   caer en "sin credenciales" con otro mensaje (Task 3).
3. **Dos altas simultáneas con 9 keys activas:** solo una debe entrar. El alta bloquea la fila de la
   empresa (`SELECT … FROM tenants WHERE id = :tenant FOR UPDATE`) antes de contar (Task 2).
4. **Key usada justo después de revocarla:** la siguiente petición debe dar 401, sin caché que la
   deje vivir unos segundos más (Task 3).
5. **Nombre con caracteres de control o solo espacios:** debe dar 400 `VALIDATION_FAILED`, igual que
   el resto de textos libres (`TextRules.NO_CONTROL_CHARS`) (Task 2).
