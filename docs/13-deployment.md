# 13 — Docker, despliegue y operaciones

## Entornos
Local (`docker compose`), staging conectado a **SRI certificación**, producción conectada solo a **SRI producción**. Keys/secretos/colas/buckets distintos. No promover artefactos con certificados de prueba a producción.

## Servicios
`api` Spring Boot, `worker` Spring Boot, `web` Next.js, `postgres`, `rabbitmq`, `redis`, almacenamiento S3 local (pendiente, ver abajo), reverse proxy TLS. En nube PostgreSQL administrado + S3 real + gestor de secretos/KMS; RabbitMQ administrado o dedicado.

## docker-compose.yml local
El archivo real es `infra/docker-compose.yml`: PostgreSQL 16, RabbitMQ 4 con su consola, Redis 7. Sus credenciales salen de las mismas `DATABASE_URL`, `RABBITMQ_URL` y `REDIS_URL` del `.env` que lee la API (ver `.env.example`): cada contenedor arranca con `infra/connection-url.sh`, que saca de su URL el usuario, la contraseña y la base, así que no se repiten en otras variables. Los puertos son fijos (5432, 5672 y 6379) y las URL deben usarlos; la consola de RabbitMQ está en el 15672 o en `RABBITMQ_MANAGEMENT_PORT`. Todos se publican solo en `127.0.0.1`. La pila completa (`infra/docker-compose.stack.yml`) usa esas mismas URL y cambia `localhost` por el nombre de cada servicio. Para operación reproducible, cambiar tags por digest. Ninguna imagen usa `latest`.

**Almacenamiento de objetos local, decisión pendiente:** el 2026-10-10 la imagen comunitaria `minio/minio` ya no se podía descargar de Docker Hub ni de Quay, por lo que `minio` no forma parte del compose. Desde el Plan 4 los XML y los certificados cifrados se guardan en PostgreSQL. Antes de producción hay que elegir un servicio compatible con S3 para desarrollo (por ejemplo una imagen de MinIO de otro distribuidor fijada por digest, u otro servidor S3) y añadirlo con su healthcheck. En nube se sigue usando S3 real. No publicar puertos de PostgreSQL, Redis ni RabbitMQ en producción.

## Variables sensibles
`DATABASE_URL`, `RABBITMQ_URL`, `REDIS_URL`, `S3_BUCKET`, `S3_ENDPOINT`, `KMS_KEY_ID`, `SRI_ENABLED_ENVIRONMENTS`, `EINVOICE_JWT_SECRET`, `EINVOICE_WEB_URL`, `SMTP_*` / proveedor transaccional. Secretos por secret manager, nunca commit. La base de datos, RabbitMQ y Redis se configuran con una variable cada una: `DATABASE_URL` (`postgresql://usuario:contraseña@host:5432/einvoice`, con parámetros como `?sslmode=require` si hacen falta), `RABBITMQ_URL` (`amqp://usuario:contraseña@host:5672`, o `amqps://` con TLS; un vhost distinto de `/` va al final, codificado) y `REDIS_URL` (`redis://:contraseña@host:6379`, o `rediss://` con TLS); los caracteres especiales del usuario o la contraseña se escriben codificados (`%40` para la arroba). Una `DATABASE_URL` o una `RABBITMQ_URL` mal formada detiene el arranque. Si la base no es solo de esta aplicación, `?currentSchema=einvoice` al final de `DATABASE_URL` la lleva a su propio esquema: Flyway lo crea y migra ese, y no toca `public`. Es lo que hace falta en **Supabase**, que deja en `public` una función propia (`rls_auto_enable`, por la que Flyway lo da por ocupado) y publica ese esquema en su API; allí, además, se usa el pooler en modo sesión (puerto 5432), no el de modo transacción (6543), que rompe los bloqueos de Flyway y las sentencias preparadas. Desde el Plan 10 la API lleva las cuentas y sus tokens: `EINVOICE_JWT_SECRET` (al menos 32 bytes aleatorios, `openssl rand -base64 48`) firma los tokens de acceso y `EINVOICE_WEB_URL` es la dirección de la web, a la que llevan los enlaces de los correos de la cuenta; sin ellas la aplicación no arranca. Esos correos salen por el SMTP de la entrega (`SPRING_MAIL_*`) con el remitente `DELIVERY_EMAIL_FROM`, aunque la entrega de comprobantes esté apagada. Desde el Plan 4 también es obligatoria `EINVOICE_MASTER_KEY` (32 bytes en Base64; se puede generar con `openssl rand -base64 32`), que protege los certificados de firma guardados: perderla los deja irrecuperables y filtrarla los expone. `EINVOICE_PROVIDER_RUC` es opcional: si se define, cada comprobante lleva el campo adicional `RUC Proveedor` (ficha, Anexo 26). Desde el Plan 7, la aplicación web necesita sus propias variables (`API_BASE_URL`, `APP_BASE_URL`, `SESSION_SECRET` de al menos 32 caracteres; ver el `.env.example` de la web): sin ellas responde con error en cuanto se usa. `APP_BASE_URL` debe ser `https` en producción para que las cookies de sesión lleven `Secure`, y el navegador no llama a la API: la web lo hace por él. La web llama a la API por su dirección interna (`API_BASE_URL`), no a través del proxy de entrada: pone ella misma la IP del navegador en `X-Forwarded-For`, y si pasara por un proxy que reemplaza esa cabecera todos los ingresos compartirían un mismo cupo. El puerto interno de la API solo debe alcanzarlo la web y el proxy de entrada. Los sistemas externos (con API key) sí llaman a la API directamente, en su propia dirección pública detrás del proxy de entrada con TLS; en esa dirección el proxy debe reemplazar `X-Forwarded-For`, no añadirse a él, y conviene que publique solo `/api/v1/**` sin `/api/v1/auth/**`, que los sistemas externos no necesitan. Desde el Plan 6, el correo de entrega está apagado salvo `DELIVERY_EMAIL_ENABLED=true`; entonces son obligatorios `DELIVERY_EMAIL_FROM` (la dirección remitente, sin nombre) y un servidor SMTP (`SPRING_MAIL_HOST`, `SPRING_MAIL_PORT`, `SPRING_MAIL_USERNAME`, `SPRING_MAIL_PASSWORD`), o la aplicación no arranca. La conexión exige STARTTLS; `SMTP_STARTTLS=false` lo desactiva y solo debe usarse con un servidor de desarrollo local. El dominio remitente necesita SPF y DKIM configurados fuera de la aplicación. Desde el Plan 5, `SRI_ENABLED_ENVIRONMENTS` decide si se transmite al SRI: vacío no envía nada, `1` solo al ambiente de pruebas y `1,2` también a producción; en producción solo debe incluir `2` después de la certificación (doc 12). `EINVOICE_WORKER_ENABLED=false` deja una instancia solo como API; al menos una instancia debe quedar como worker.

Desde el Plan 6b: `EINVOICE_WEBHOOKS_ENABLED` (por defecto `false`) enciende los avisos a sistemas de los clientes; debe valer lo mismo en la API y en el worker. El worker necesita entonces salida a internet por `https`, y conviene que esa salida no alcance la red interna (doc 10). `EINVOICE_WEBHOOKS_ALLOW_INSECURE_HTTP` y `EINVOICE_WEBHOOKS_ALLOW_PRIVATE_ADDRESSES` son solo para desarrollo. RabbitMQ gana la cola `webhook.deliver` y su cola de mensajes muertos, que se declaran solas. Desde el Plan 8: `EINVOICE_METRICS_TOKEN` (al menos 24 caracteres) abre las métricas de `/actuator/prometheus`; sin ella no existen. `EINVOICE_RATE_LIMIT_REQUESTS` y `EINVOICE_RATE_LIMIT_WRITES` cambian el cupo por usuario y minuto (1200 y 300); `REDIS_TIMEOUT` (500ms) es cuánto se espera a Redis antes de seguir sin él. `SPRING_FLYWAY_USER` y `SPRING_FLYWAY_PASSWORD` permiten migrar con un usuario distinto del que opera (`infra/postgres/roles.sql`). En la web, `API_TIMEOUT_MS` (30000) es cuánto se espera a la API. `LOGGING_STRUCTURED_FORMAT_CONSOLE=ecs` pone los registros de la API en JSON.

## Imágenes y staging de referencia
El `Dockerfile` de este repositorio y el de [la web](https://github.com/DevNation593/client-factura-facil) construyen `einvoice-api` (API y worker, según `EINVOICE_WORKER_ENABLED`) y `einvoice-web`; ninguna corre como root. `infra/docker-compose.stack.yml` las levanta sobre la infraestructura del compose, con solo la web publicada, e `infra/stack-smoke.sh` comprueba el resultado. Con solo la web publicada, un sistema externo no llega a la API: para usar API keys hay que publicar también la API detrás del proxy de entrada (solo `/api/v1/**`, sin `/api/v1/auth/**`), mientras la web sigue llamándola por la red interna. Es una referencia, no un despliegue: no hay proxy TLS, ni registro de imágenes, ni nube elegidos, y las imágenes base van por etiqueta, no por digest.

## CI/CD
Objetivo: format + tests + SAST/SCA + SBOM -> build OCI -> firma/scan de imagen -> migración Flyway controlada -> deploy canary -> smoke test -> rollback de aplicación sin revertir arbitrariamente migraciones destructivas. Test de restore previo a grandes cambios.

Desde el 2026-10-13 el sistema vive en dos repositorios públicos de DevNation593, cada uno con su workflow. El de este hace: pruebas de la API, cobertura mínima de los paquetes críticos, SBOM, verificación de los XSD, pruebas con navegador del recorrido completo, y construcción de la imagen. El de [la web](https://github.com/DevNation593/client-factura-facil): lint, tipos, pruebas, auditoría de dependencias, SBOM, imagen y la comprobación de que su copia del contrato es la de este repositorio. No firman ni analizan imágenes, no publican y no despliegan. No usan Code Security de GitHub (ni revisión de dependencias en los pull requests ni Dependabot): las dependencias de Maven no tienen comprobación de vulnerabilidades en CI; las de npm sí (`npm audit`).

## SLO, backup, alertas
Objetivo: monitorear p95 API, colas, SRI, DLQ, disco, conexiones, certificaciones, expiración certificados y almacenamiento. Backup diario con PITR PostgreSQL y versionado objetos; RPO/RTO aprobados; restauración ensayada. Job reconciliador de estados SRI y verificador de hashes de objetos.

Hoy existen las métricas de comprobantes, colas, outbox, entregas, certificados, artefactos y llamadas al SRI, con sus alertas de partida (`infra/observability/prometheus-alerts.yml`); los scripts de respaldo y restauración, ensayados en local; el reconciliador y el verificador de huellas. Faltan p95 de la API como objetivo, disco y conexiones, PITR, RPO y RTO acordados y un Prometheus desplegado. Detalle en el [doc 15](15-produccion.md).
